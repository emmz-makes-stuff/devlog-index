# Section 13 done: review fixes for index integrity and model pinning

These come from the code-review run (the 1710 note).

- **13.1** `updateAt` now runs `BEGIN IMMEDIATE` before it reads `files`. Embedding was already inside
  the transaction, so the lock is held only a little longer, for the snapshot and chunking.
  - **Finding:** the first busy point is actually `Index.open`. It takes its own `BEGIN IMMEDIATE`
    for schema setup, so a concurrent update blocked there and then failed with the bare
    "update failed (SqliteBusy)".
  - The "locked by another devlog-index update; the index is unchanged; try again when it finishes"
    message now lives in `update.run`'s error mapping, so it covers both points.
  - The test can't stage the race any more once the read is under the lock, so it holds the write lock
    from a second connection. Task 13.1's wording now says this.
  - `db.busy_timeout_ms` is a new `pub var` (default 5000). The test drops it to 50 ms and restores
    it. I first tried a per-update `Options` field, but `Index.open` opens its own connection, so a
    module default was simpler.
- **13.2** `query.load` skips a ranked passage that has no file row, counts it, and returns
  `Loaded { results, orphans }`. `run` adds the notice "N ranked passages belong to no indexed file and
  were skipped; rebuild the index with: …". In the test, the deleted row also raises a staleness
  notice, which is correct, so the test checks the last notice.
- **13.3** On the no-live-index path, `swapIn` calls `deleteDbFiles(live)` before the rename.
  `swapIn` now takes `arena`. The test calls `swapIn` directly with stale `-wal`/`-shm`/`-journal`
  files present.
- **13.4** The model is now pinned by content.
  - `model_url.pinned_url` now names commit `0188c9bf409793f810680a5a431e7b899c46104c`, HF `main`
    as of 2025-04-28 ("cleanup").
  - `pinned_sha256` = `0c7930f6c4f6f29b7da5046e3a2c0832aa3f602db3de5760a95f0582dbd3d6e6`. That's the
    LFS oid from the HF API, and it matches `shasum -a 256` of the cached GGUF (99,588,928 bytes).
  - `download.copyVerified` streams through an `Io.Writer.Hashed(Sha256)` layered between progress
    and the file. On a mismatch the atomic temp is never renamed, so nothing is cached, and `download`
    logs both hashes.
  - **Gotcha:** the Zig test runner fails any test that logs at `.err`. So `copyVerified` returns the
    actual hash through a `got` out-param, and the log line lives in `download`.
  - An already-cached file isn't re-hashed, because that would cost every query. This is now in D2.
  - A new test checks that the pinned URL names a 40-hex commit and caches at the same path as the old
    `main` URL, so there's no new download.
  - The spec gained a separate requirement, "Model pinned by content", with a hash-mismatch scenario.
    Putting it inside the existing requirement pushed its text past openspec's 500-character limit
    (`VALIDATE_EXIT:1`).
  - D2 and `docs/dependencies.md` mention the pin.
