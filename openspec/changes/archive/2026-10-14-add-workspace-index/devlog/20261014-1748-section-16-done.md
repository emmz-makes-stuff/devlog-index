# Section 16 done: review fixes for index swap and concurrency

<!-- Section: 16 · Tasks: 16.1–16.4 · Base: a148bdf -->

These are findings 1–4 from the second code-review run (the 1744 note). Emmz agreed the tasks, and
chose to fail a second rebuild rather than make it wait.

- **16.1** `runInner` (rebuild only) takes an exclusive, non-blocking lock on `index.db.rebuild.lock`
  through `createFile(.{ .lock = .exclusive, .lock_nonblocking = true, .truncate = false })`.
  - `WouldBlock` is mapped to `error.SqliteBusy`, so the existing message in `run` applies:
    "… is locked by another devlog-index update; the index is unchanged; try again when it finishes".
  - The lock file is left on disk on purpose, because deleting it would race the next rebuild's lock.
  - Test: hold the lock from the test and pre-write `index.db.rebuild`. The rebuild fails with the
    message, embeds nothing, and leaves that file and the live index alone.
- **16.2** `swapIn` checks the live file with the new `readable(live)`.
  - `readable` opens the file read-only and runs `SELECT count(*) FROM sqlite_schema`. It returns
    false on `SqliteOpenFailed` or `SqliteFailed` (NOTADB or corrupt), and passes `SqliteBusy` up,
    because a lock doesn't mean the file is unreadable.
  - When it's false, `swapIn` deletes the live files and renames the build into place, the same path
    as "no index yet".
  - Test: `index.db` holds text and `index.db-wal` holds "stale". `update --rebuild` adds 19, and the
    stale WAL is gone.
  - **Gotcha:** the rebuilt index is in WAL mode, so an `index.db-wal` can exist again afterwards. The
    test checks that its content isn't the stale content, not that the file is absent.
- **16.3** `swapIn` treats only `FileNotFound` from `access(live)` as "no index". Any other error is
  returned before anything is deleted.
  - Test: `index.db` is a symlink to itself, which gives a loop error. `swapIn` fails, the
    pre-written `-wal` survives, and the build file isn't renamed.
- **16.4** `query.runInner` runs `BEGIN` straight after `openRead` and defers `COMMIT`, so staleness,
  rank and load all read one WAL snapshot.
  - A test-only hook, `test_between_rank_and_load` (`{ ctx, run }`, called only under
    `builtin.is_test`), runs between rank and load. That's the same idea as `db.busy_timeout_ms`.
  - Test: a baseline query, then the same query with a hook that deletes every passage and file from
    another connection. The results (paths and text) and the notice count match the baseline, and
    the rows are really gone afterwards.
- **Mutation-checked:** removing `BEGIN`, widening the `access` catch, or forcing `readable` to true
  each makes its test fail. Without the lock, the 16.1 test would delete the pre-written build file,
  so it fails too.
