# Section 5 done: index storage and incremental update

- 5.1 `src/db.zig` (thin SQLite wrapper) and `src/index.zig` (D3 schema). `settings` holds the schema
  version, model URL (pinned when the index is created), `dim` (pinned at the first embedding, when the
  `passages_vec` vec0 table is created) and `last_update`. `files` also stores `size` and `mtime_ns`, for
  §6's freshness check. `passages` has a `text_hash` index. `passages_fts` is a plain FTS5 table (porter)
  whose rowid is the passage id. A different model URL, schema or dimension is refused with a message
  naming both and `devlog-index update --rebuild`.
- 5.2 `src/update.zig` and `update [--rebuild]` in `main.zig`. Discover, snapshot (stat, read and hash
  every file first), compare hashes with `files`, then apply everything in one `BEGIN IMMEDIATE …
  COMMIT`. New passages are inserted before stale ones are deleted. `--rebuild` builds
  `index.db.rebuild` and renames it over `index.db`. The model comes through a `Provider` and is loaded
  only when a passage needs embedding, so a no-change run never loads it. `ModelProvider` downloads it on
  first need via `download.ensureCached`. Tests use a stub embedder (8-d, hash-derived) on a temp copy of
  the fixture, covering every Incremental update scenario plus edits, model load failure, an
  interrupted embedding, a missing member, mismatch then rebuild, and progress. One model-gated test
  runs a full update with the real model (768-d). With `DEVLOG_INDEX_TEST_MODEL` set: 55/55.
- 5.3 Real workspace: `init` with the five members agreed with Emmz, then `update`. **3,048 passages
  from 764 files, full build 730 s (12.2 min)**. Passages by kind: section 795, stopped 499, spec 352,
  note 345, tasks 317, design 215, decision 206, proposal 159, change 112, spec-delta 29, answer 12,
  review 11. Next run (2 files had changed meanwhile): 1.7 s including model load. A no-change run:
  **0.09 s**, "0 files changed".

Emmz's answers (asked during the section):
- A missing member's passages are **kept** (with a warning). Removing the member from the config drops
  them. `--rebuild` can't keep them, so its warning says the member is left out.
- **Reuse vectors by exact passage text** (sha256 `text_hash`). Archiving a change costs no embeddings;
  editing a file re-embeds only the passages that changed.
- Build speed: **more CPU threads**. `embed.embedThreads()` reads `hw.perflevel0.physicalcpu`, which is
  10 on this machine, and falls back to the logical CPU count; llama.cpp defaults to 4. This took
  385 ms/passage down to 240 ms/passage. Metal was offered and not chosen: it would reverse ADR-0001.
- **Progress on stderr**: "N passages to embed", then "embedded i/N" every 100 and at the end. The count
  comes from a pre-pass that excludes passages whose vectors can be reused.

Gotchas:
- The first real run failed after 985 s with `FileNotFound`. Other sessions were writing notes in the
  workspace, and the file reads were interleaved with slow embedding. It rolled back cleanly (index
  unchanged, as designed). Fix: snapshot every file before embedding; a file that vanished since
  discovery counts as gone; other read errors name the path. Stat comes before read, so a change between
  them leaves an older mtime and the next freshness check notices it.
- `SQLITE_TRANSIENT` can't be expressed in Zig (a misaligned function pointer, even at comptime).
  `db.zig` declares `sqlite3_bind_text`/`_blob` with an `isize` destructor and passes -1.
- The `sqlite3` CLI has no vec0. Anything touching `passages_vec` must go through the binary or tests.
- `sysctl` and `pgrep` fail inside the sandbox ("Operation not permitted"). In-process `sysctlbyname`
  works unsandboxed. A sandboxed run would fall back to the logical CPU count.

Deferred and open:
- **Readers during a long update (question for Emmz, in §6/§7):** in rollback-journal mode a 12-minute
  write transaction blocks `status`/`query` once it spills to disk (busy timeout 5 s). WAL mode would let
  readers see the previous snapshot, but `--rebuild` renames the database file, which needs care with
  `-wal`/`-shm` files. Not changed in §5.
- If a directory vanishes in the middle of discovery's walk, the update still errors (a tiny window,
  milliseconds). Not handled.
- Downloading the model on first need isn't covered by an automated test (it needs the network). That
  path is `download.ensureCached`, unchanged since §2.

Self-review: matches Incremental update, Local embeddings (pinning, mismatch, load failure, download on
first need) and Workspace data stays beside the config. Errors reach the user through `Diag` with the
path or the models named; nothing is swallowed except best-effort progress writes.
