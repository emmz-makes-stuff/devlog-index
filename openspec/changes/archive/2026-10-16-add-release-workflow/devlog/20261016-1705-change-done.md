**Review result: no defects found, no fix section needed.**

- **Duplicated abstractions:** none. The Zig install step is repeated verbatim in `ci.yml` and `release.yml`
  (same pinned URL and checksum). Accepted: two small workflows, and a shared composite action would be more
  machinery than the duplication costs. Bump both together when Zig moves.
- **Leftover scaffolding:** none. The spike workflow and the temporary branch trigger are both gone;
  `release.yml` triggers only on `v*` tags and `workflow_dispatch`.
- **Cross-section drift:** none. Targets `macos-arm64`/`linux-x64`/`linux-arm64` map to
  `aarch64-macos`/`x86_64-linux`/`aarch64-linux` in `release.yml`, the `case` in `package-release.sh`, the
  README table and the spec. `make gates` includes `test-scripts` (`SCRIPTS_EXIT`).
- **Spec satisfied:** every requirement maps to something concrete.
  - Targets, packaging and checksums: the build loop, `package-release.sh`, `checksums.sh`.
  - Tag publishing: the `publish` job, gated on `refs/tags/v*`, with `--verify-tag` and `--prerelease` for
    tags containing `-`.
  - Manual dry run: `build` uploads the `release` artifact and `publish` is skipped on dispatch.
  - CI: `ci.yml` runs fmt and test on push and PR.
  - Design decisions are followed: the `build`/`publish` split, read-only `build` permissions, SHA-pinned
    actions, and the smoke test before publish.
- **Not exercised, structurally guaranteed:** the "a target fails → no Release" scenario was never run
  with a failing target. `publish` has `needs: build`, and the build step runs under GitHub's default
  `bash -e`, so a failed target fails `build` and skips `publish`.
- **Not verified:** a real tag-push release. The 4.2 dry run was a dispatch/branch run, and the README's
  URL commands were checked against a `file://` copy of the assets. Re-check after the first real tag.
